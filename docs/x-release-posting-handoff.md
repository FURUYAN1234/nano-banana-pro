# X更新告知の引き継ぎ

この手順は、既存のFourPanel note記事を更新する実質的なNano Banana Proリリースに適用する。ユーザーは2026-09-26に、今後のnote更新と一緒にXでも新機能を告知するよう依頼した。誤字、数pxの調整など利用者への説明を要しない小修正はX投稿を省略できる。機能追加、大きな使い勝手の改善、利用方法の変更など、note以外にも知らせる価値がある場合は告知する。境界が曖昧な時や別製品の節目は、投稿に向く理由をユーザーへ提案する。

## 公開先と順番

1. 公式リリースを完了し、公開アプリと配布リンクを読み戻す。
2. [既存のnote記事](https://note.com/happy_duck780/n/ndf063558c1f5) を更新し、公開ページの現行タイトル・本文・履歴・図版・リンクを確認する。
3. Xの [@FURUYAN123456](https://x.com/FURUYAN123456) で、利用者に伝わる変更だけを1件投稿する。GitHubの所有者名 `FURUYAN1234` とXの投稿アカウント `FURUYAN123456` は別なので、送信前に表示中のXアカウントを確認する。
4. 送信済み通知だけで終えず、公開ポストの固有URLを開き、本文・改行・アプリURL・note URL・ハッシュタグを読み戻す。成否が不明な場合はプロフィールの最新投稿を先に確認し、同じ文章を重複投稿しない。

別PCではCodex内蔵ブラウザを優先し、Xに未ログインならユーザーがそのPCでログインする。パスワード、認証コード、Cookie、APIキーをチャット、引き継ぎ書、Git、バックアップ用の追加ファイルへ転記しない。ブラウザのログイン状態はPC間で引き継げる前提にしない。

## 文面の作り方と公開ゲート

- 記事の見出しに合わせ、利用者向けには「完全自立型AIまんがエンジン」または「Super FURU AI 4-koma System」を用いる。`Nano Banana Pro` のみを見出しにして内部管理名だけの告知にしない。
- リリースノートと実画面で確認済みの改善だけを書く。画質向上、完全再現、API上限、料金など、今回検証していない成果を約束しない。
- 本文は **見出し、変更点、アプリURL、note URL、ハッシュタグ** の順で明確に改行する。複数の変更点を一行へ詰めすぎず、文章の途中に不自然な改行を入れない。X上の折り返し表示と、投稿データの実際の改行は区別して確認する。
- アプリの公開先は `https://furuyan1234.github.io/nano-banana-pro/`。noteは上記の既存記事。関連するハッシュタグを2～3個だけ付ける。Xの標準文字数カウンターが上限内であることを送信前に確認する。
- 個人情報、連絡先、APIキー、認証情報、ローカルパス、内部ログ、未公開の入力・画像、未確定の障害原因を含めない。本文とURLを目視で確認し、必要なら対象語の検索も行う。これらの確認を省略して自動送信しない。
- noteのカードプレビューに古い版の見出しがキャッシュされることがある。表示が古ければXの「カードプレビューを削除」でカードだけ外し、本文のnoteリンクは保持する。
- 送信後の証拠は、公開ポストURL、投稿アカウント、実際の本文、X上の残り文字数（送信前）、リンク先、投稿時刻。公開URLが得られない場合は投稿済みと記録しない。
