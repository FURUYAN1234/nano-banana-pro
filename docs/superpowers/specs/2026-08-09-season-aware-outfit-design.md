# 季節連動衣装選定 設計

## 目的

ニュース検索で指定した対象日付と漫画の服装を整合させる。特に、夏祭りで冬服、真冬の屋外で薄手の夏服といった明白な不整合を防ぐ。一方で、現在の操作手順、手動の指定服装、イベント固有衣装、職業上の衣装、屋内環境を壊さない。

## 適用範囲

- 対象日付による自動季節判定はニュース検索モードだけに適用する。
- 手動トピックでは対象日付を自動適用しない。ただし、入力本文に明示された季節、天候、催事、場所は衣装選定の必須条件として扱う。
- STEP2 の衣装自動選定と、その結果を利用する既存の STEP3・STEP4 衣装継続経路を対象とする。
- 公開、リリース、バックアップ、他アプリの変更は対象外とする。

## 季節判定

日本の一般的な暦を既定値として、対象日付の月から次の季節目安を決定する。

- 春: 3月から5月
- 夏: 6月から8月
- 秋: 9月から11月
- 冬: 12月から2月

日付が空または不正な場合は季節判定を行わず、既存の場所・状況に基づく衣装自動選定へ戻す。例外やタイムゾーン変換で月をずらさないよう、`YYYY-MM-DD` の月部分を直接、安全に解釈する。

## 衣装決定の優先順位

衣装は次の順序で決め、上位の条件を下位の条件で上書きしない。

1. ユーザーが入力した指定服装
2. トピックやイベントに明示された固有衣装
3. 職業、安全装備、場所、天候、屋内外の環境条件
4. 対象日付から求めた季節目安
5. 従来の AI おまかせ衣装

例:

- 8月の夏祭りでは、浴衣、甚平、通気性のよい夏服などを候補にする。防寒着を選ばない。
- 8月でも屋内スケート場、冷凍倉庫、雪山など、明示的に寒い環境では防寒寄りの衣装を許可する。
- 海外の場所が明確で、現地の季節や気候がトピック本文から判断できる場合は、対象日付だけで決めた日本の季節目安より現地条件を優先する。
- 指定服装に冬服が入力されている場合は、夏の日付でもユーザー指定をそのまま優先する。

## データフロー

1. ニュース検索モードの `targetDate` から、独立した純粋関数で季節コンテキストを生成する。
2. STEP2 のシナリオ生成プロンプトへ、対象日付、季節名、一般的な気候目安、例外の優先順位を渡す。
3. AI は場所、天候、イベント、職業を考慮し、細かすぎない衣装カテゴリーを `Outfit:` に一つ出力する。
4. 既存の `Outfit:` 解析、`lockedOutfit`、STEP3 の各コマ衣装注入、ChatGPT/OpenAI と Gemini の衣装継続ロックをそのまま利用する。
5. 季節コンテキストは内部の選定根拠として扱い、新しい `Season:` 行をシナリオ本文へ追加しない。これにより、既存のシナリオ解析や吹き出し抽出へ新しい構造行を増やさない。

## UI

新しい選択欄や春夏秋冬ボタンは追加しない。ニュース検索モードの対象日付付近に、次の読み取り専用表示だけを追加する。

`季節目安: 夏（対象日付から自動）`

手動トピックモードではこの表示を出さない。指定服装入力と Generation Preview の `Outfit:` 編集経路は従来どおり維持する。

## 出力検証とエラー表示

AI の `Outfit:` が空、曖昧、または季節コンテキストと明白に矛盾する場合は、具体的な検証理由を返す。例外環境がトピック、場所、天候に存在する場合は矛盾と判定しない。

代表的な検出例:

- 夏または夏祭りに、理由なくダウンジャケット、厚手コート、マフラー、防寒着を選ぶ。
- 冬の屋外に、理由なく水着、薄手の半袖などを選ぶ。
- `Outfit:` が空、`デフォルト`、`キャラシート準拠` だけで終わる。

検証NG時は、`夏（8月）なのに防寒着が選ばれました` のように、対象フィールドと不整合を進捗表示へ出す。自動修正経路を利用してもよいが、実装の合格条件は代表サンプルが再試行なしの初回生成で有効な衣装になることとする。

## 実装境界

- 季節計算は `src/lib` 配下の小さな純粋モジュールとして分離し、プロンプト文字列の内部へ月判定を埋め込まない。
- プロンプト生成側は季節コンテキストを受け取り、優先順位と例外を明示する。
- 出力検証は既存のシナリオ生成・検証経路へ最小限に統合する。
- UI は既存のニュース日付欄と Generation Preview の構造を保つ。
- キャラクター名、特定ニュース、特定人数を本番コードへハードコードしない。

## テスト

### 単体テスト

- 3月、6月、9月、12月と各境界月が正しい季節になる。
- 不正日付と空日付が季節なしになる。
- ニュース検索モードだけが対象日付の季節コンテキストを使う。
- 手動トピックは対象日付に拘束されず、本文の明示季節・催事を優先する。
- 指定服装が常に最優先になる。
- 8月の夏祭りで冬服が明白な矛盾として検出される。
- 8月の屋内スケート場では防寒着が許可される。
- 冬の屋外で理由のない夏服が矛盾として検出される。
- `Outfit:` が STEP3 と両画像プロンプト系へ継続する既存契約が壊れない。

### 全体検証

- 関連テストと全 Node テスト
- ESLint
- Vite production build
- `git diff --check`

### 実API画像検証

- 必須ブラウザ面は in-app browser とする。
- APIキー値は読み取らず、UIのマスク状態または安全な接続状態だけを確認する。
- ニュース検索モードで夏の日付と夏祭りに相当する入力を使用する。
- STEP2 の初回出力で季節に適合する `Outfit:` が選ばれ、明白な冬服が含まれないことを確認する。
- 編集していない通常の STEP3 出力を使用して、実画像APIで4コマ画像を一度生成する。
- 最終画像をフル解像度で確認し、夏祭りの状況に合う衣装であり、冬服、コマ間の衣装変化、明白な人物破綻がないことを確認する。
- 自動テスト、プロンプト確認、過去画像は実API画像検証の代替にしない。

## 完了条件

- 対象日付と衣装の季節連動がニュース検索モードで動作する。
- 手動指定、イベント、職業、場所、天候の優先順位が守られる。
- UIに季節目安が表示されるが、操作手順は増えない。
- 代表的な季節不整合が具体的な理由で検出される。
- 自動検証がすべて通る。
- in-app browser の実APIシナリオ生成と実API画像生成で、夏祭りに冬服が出ないことが初回生成から確認できる。
